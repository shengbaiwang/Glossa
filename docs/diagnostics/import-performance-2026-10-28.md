## 为什么每四本刷新

- `src/app/library/page.tsx:928` 固定 `concurrency = 4`，按四本切片，等待整个 `processBatch` 后才调用 `updateBooks` 和进度回调，再开始下一批。
- `src/services/bookService.ts:935` 用 `Promise.all` 等待本批全部准备和暂存；随后在同一书库锁内逐本提交，保存成功后发布。本批快文件会等待慢文件，空出的准备位置不会提前接收下一批。
- 因此 33 个输入通常显示 0、4、8、12……32、33。这里是已处理输入计数，包括已存在和失败项，不保证等于新增书籍数，也不是按字节或耗时计算的进度。
- 四本有助于限制同时解析的资源，并将书库读写合并为批次；未找到四本是此机器／此材料最优并发值的基准证据。

## 当前仍有的耗时路径

1. **整批等待与反馈空窗。** 下一批必须等待最慢准备项、本批串行提交和暂存清理全部结束；批内没有文件名、核验／解析／复制阶段进度。此结构同时影响吞吐和用户判断是否仍在工作。
2. **完整文件 I/O。** `bookService.ts:448` 首先完整 SHA-256；普通本机新书在 `:570` 复制时再次读取并计算指纹，核对源文件未变化。`import_io.rs:124`、`:141` 确认两条流式路径。已省去复制后的独立完整重读，但不等于只读一遍；原位导入也在 `bookService.ts:545` 重新完整核验。解析另有按格式读取，不能把这些安全核验直接删掉。
3. **解析及封面仍在发布前。** 本机 EPUB／MOBI 有快速解析路径；其余走 `DocumentLoader.open()`。PDF 仍初始化 PDF.js，读取首页、元数据、嵌入目录与页码标签，并渲染首页封面（`packages/foliate-js/pdf.js:632`、`:662`、`:913`）。TXT 转换、Markdown 资源快照也属于准备阶段，单纯更改并发不能消除这些成本。
4. **重复文件仍先解析。** 完整指纹计算后没有直接结束已有记录路径；先完成文档解析，才在暂存／提交时判断已存在。已知重复可跳过复制与封面，但仍承担此前解析。可研究核验身份后的早期复用，必须保留缺失文件恢复、个人记录保护和主动 PDF 目录重试语义。
5. **锁内仍有逐本文件操作。** `bookService.ts:989` 顺序提交；提交包含目录／文件存在检查、移动、封面写入及封面哈希、配置初始化、封面 URL；旧候选缺指纹时还可能在锁内完整核验（`:660`）。每批只逻辑保存一次书库，但仍合并并序列化整份书库，`persistence.ts:72` 先写备份再写主文件。小书库中未证明这是主要耗时，大书库及旧记录需单独测量。
6. **后台目录的间接竞争。** `bookService.ts:910` 已经不等待 PDF 自动目录；`pdfAutoContents.ts:625` 将目录任务顺序排队。等待的任务继续持有其文档，完成后才释放；批量 PDF 可能与后续导入竞争资源。这里只确认调度和生命周期，未测得实际内存峰值或资源争用占比。
