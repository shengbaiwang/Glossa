# 阅读设置操作后书库封面异常：排查与修改方案

日期：2026-11-05（Asia/Singapore）。状态：用户已授权并落实源码修复；验证结果及仍未锁定的首次触发原因分列如下。日常安装版已于同日后续维护中替换；启动截图仍见文字后备封面，尚不能认定完整生产现场问题已解决。详见 `PROGRESS.md` 的正式安装记录。

## 结论与证据等级

用户补充的触发动作是「在阅读界面点击右上角设置」。截图可确认的现象是书库图片封面整体变为纸色文字后备，书名、分组、数量和阅读状态仍有显示。

**已修复“失败后同地址不再重试”、封面版本未失效及设置布局页的缺省配置误保存；尚未证明截图中点击设置为何导致首次图片失败，也未在用户当前完整应用中复现整架退化。** 因此不能把“设置直接改坏书库”“PDF 损坏”“GPU 故障”或“多窗口必然冲突”当成已确定根因。

### 本次落实

- `BookCover` 使用书籍身份、来源及 `coverHash/coverUpdatedAt` 标识请求，与阅读进度时钟分离；原成功图片节点及比例在新图加载期间保留，新图有有效尺寸后才切换。主动清空封面会清除旧成功状态，另一本书不继承旧图。
- 首次错误后自动重试一次；继续失败使用文字后备，等待窗口 focus、成功的全量书库刷新或封面版本变化后恢复，不持续计时重试，也不因每次进度保存重试。仅本机地址增加版本查询参数，远程签名 URL、Blob 和 data URL 保持原值。旧请求回调不能覆盖新身份。
- 保存成功的通知只附变更书籍 hash；书库已完整加载时按这些身份读取、合并记录，保留未涉及书籍的可用封面与成员。兼容旧无载荷通知；focus、删除、关闭阅读器共用刷新协调入口，合并突发请求、串行读取，并在失效后重读而不发布迟到快照。失败保留现有书架及后续重试机会，沿用已有逐字段合并。
- 找到额外确定缺陷：旧本书配置未含 `webtoonMode/contrast` 时，进入 Layout 会把界面默认值与 `undefined` 比较，触发两次强制保存。已统一缺省值比较，PDF／EPUB 打开 Font、进入 Layout、关闭均验证不保存。**右上角默认打开的是 Font，而不是 Layout；这两次保存不能直接解释“只点击入口”的截图事故。**
- 新增默认关闭、最多 200 条的本机会话诊断。设置开关／挂载、刷新开始／完成／失败及图片加载／错误记录事件和安全数值，不记录路径、书名、正文或原始异常，不发送遥测。对应 WebView 调试控制台设置 `sessionStorage.setItem('glossa-library-diagnostics', '1')` 后再复现；读取 `sessionStorage.getItem('glossa-library-diagnostic-log')`，设置为 `0` 即停用。该开关不追溯截图发生时的事件。

### 进一步调查所得

54 个现存封面随后全部经 Apple ImageIO 只读解码成功（54 成功、0 失败），进一步排除“全部封面文件损坏”。真实设置入口、真实 lazy SettingsDialog／FontPanel／LayoutPanel、真实设置与书库 store，以及进度通知均已在 Chromium 和隔离系统 WKWebView 夹具中验证；没有复现仅打开设置导致封面错误。原生还使用真正的临时 PNG 和 Tauri asset 协议验证缺失后的恢复与同路径换图。

现有证据能解释错误发生后为何持续变成文字封面，并修复会扩大刷新范围的链路；不能还原截图时首次 error 的来源。剩余现场工作是完整 PDF 阅读窗口与书库窗口往返的生产版追踪，包括设置模块首次加载、窗口重建和图片 error 的先后关系。本次组件集成夹具没有打开完整 PDF 阅读引擎，也不能代替用户当前日常应用现场复现。

## 修复前代码定位

### 1. 确定缺陷：图片失败状态无法随同地址刷新恢复

`apps/readest-app/src/components/BookCover.tsx:29–38,58–80`：

- 图片状态只以 URL 为身份。
- `onError` 将状态设为 `error`，渲染条件随后彻底移除 `<Image>`。
- 书库后续加载到同一 URL，即使文件仍可读取，组件仍沿用 `error`，没有新的图片元素，也没有重试机会。
- `coverHash`、`coverUpdatedAt` 没有参与加载身份。本机地址又固定为 `<book hash>/cover.png`（`services/bookService.ts:235–259`、`utils/book.ts:39`）。因此同路径更新封面也没有完整的版本失效契约。
- `onLoad` 未将 `naturalWidth/naturalHeight > 0` 作为成功的必要条件；失败／空尺寸与成功的判定也应收紧。

这是“为什么文字后备会一直保持”的确定问题，**不是首次错误触发的证明**。

### 2. 阅读操作与书库存在共享刷新链路

`services/libraryService.ts:62–69` 在持久保存成功后广播书库更新；`hooks/useLibraryRefresh.ts:14–26` 收到广播或书库窗口 focus 时，重读整份书库并重新生成所有封面地址。

原生地址通常保持相同，因此不能把“重新生成地址”误说成“每次都重新下载图片”。但这一刷新无法解除上面的错误状态，也没有区分纯进度变更和封面变更。异常被空 catch 吞掉，现场难以判断是数据库重读失败、资源加载失败还是显示状态问题。

该 hook 已有请求序号保护，不能说它完全没有竞态保护。阅读关闭事件在 `app/library/page.tsx:502–512` 另走一条重读流程，删除事件也有独立重读流程；各入口尚未共享同一协调序号。

### 3. 仅打开设置不能认定为写坏书库

阅读右上角入口 `app/reader/components/SettingsToggler.tsx:27–30` 只设置阅读面板开关和当前书籍；菜单中的全局设置入口同样调用 `openSettingsDialog`。这些开关是各 WebView 内的 Zustand 状态，不是跨窗口广播字段。

`ReaderContent.tsx` 使用 React.lazy 首次加载 `SettingsDialog`。本次没有捕获到当时的设置模块加载失败、WebView 重建、图片错误事件或对应调用栈，故不能直接将这一点击与全架图片错误连成已证实因果链。

## 修改方案

### A. 先补齐首次失败的可观测性（最高优先级）

在隔离开发环境复现「PDF 打开 → 点击右上角设置 → 书库保持打开 → 切回书库」，同时记录：

- 窗口角色、事件类型、相对时间、刷新序号与变更种类。
- 图片是否挂载、加载身份、complete／naturalWidth、load／error、后备状态、解码结果；资源请求仅记录协议与错误分类，不记录完整路径、书名、正文或凭据。
- 设置 lazy 加载异常、错误边界／自动 reload、进程重启，以及书库重读失败。

使用有界本机诊断缓冲；不增加常驻 UI 或遥测。首次打开、重复打开、只打开不修改、修改本书设置、改全局设置分别验证。对照今天生产构建，不能只测开发热更新。

### B. 修复已确认的封面恢复缺陷（最小实质修复）

1. 加载身份使用「书籍身份＋来源＋封面版本」，独立于阅读进度时间戳。显式删除封面应使用新的空封面版本，不能沿用旧成功图。
2. 将加载中、成功、暂时失败、确认无封面区分；保留现有纸色后备。首次临时失败允许一次有界重试；再次失败等待明确刷新／封面版本变更，不无限循环，也不每次翻页重试。
3. 普通进度刷新保留成功图与长宽比；新的封面成功解码后再切换。旧任务的成功／失败回调不得覆盖新版本。
4. 成功判定要求有效图片尺寸；失败保留局部恢复机会。没有封面的测试书仍稳定使用文字卡片，不反复请求不存在的文件。
5. 本机图片是否改用原生 `<img>`，待 A 的证据决定。现有 Next Image 正常路径已通过，不把换组件作为未经验证的必需修复。

### C. 收敛跨窗口刷新边界

- 事件提供最少的变更身份和种类，例如 progress／metadata／cover／membership；旧版无载荷通知继续作为全量失效处理，不在事件里传书籍正文或临时 Blob URL。
- 优先沿用 Repository 已支持的按 hash 读取：纯进度更新合并对应记录，保留本窗口可用封面资源。删除、归组和导入继续维护真实成员关系。
- focus、普通广播、关闭阅读器和删除通知共用一个刷新协调入口；单次在途、合并后续请求、丢弃迟到结果。失败保留现有书架并记录可诊断原因；需要用户处理时沿用轻量提示和重试。
- 保留现有逐字段元数据／分组／阅读状态合并，不能通过整对象替换重新引入旧阅读窗口覆盖较新编辑。

### D. 设置操作保持局部

- 单纯打开／关闭面板只读配置，不保存书库、不改变封面、不改变目录与选中项。通过集成断言覆盖 Font 和 PDF Layout 子页，而非把真实子组件全部 mock 掉。
- 本书偏好继续只作用于当前书；主动设为默认或修改全局字段才广播相应变化。
- 若 A 证实设置模块加载／面板异常触发全页重载，给设置模块增加局部错误恢复，使阅读位置和其他窗口继续可用。没有证据前不扩建全局窗口管理系统。

## 验收与交付顺序

先保留能复现 B 的失败测试，再做 B 的最小修复；A 的现场观测与 B 同批进行，按证据确定是否需要额外处理设置模块或原生资源。C 按进度刷新和全量刷新分两步落地。

| 场景 | 必须满足 |
| --- | --- |
| 阅读 PDF／EPUB 时首次和重复打开设置 | 书库封面、布局、搜索、滚动与选择保持；阅读窗口继续打开 |
| 只更新阅读进度 | 对应进度与最近阅读更新，已成功封面不重置 |
| 单图临时失败后恢复 | 有界恢复，其他书卡不受影响 |
| 相同文件路径替换封面 | 新版本确实显示；旧回调不能覆盖 |
| 真正无封面／主动清空封面 | 稳定文字后备，无无限请求 |
| 多窗口、慢响应、乱序与数据库失败 | 不覆盖较新编辑，不清空书架，可重试 |
| 分组预览、最近阅读、网格与列表 | 统一封面身份和恢复语义 |
| 深色、窄屏、RTL、电子墨水 | 沿用现有平面封面和交互，无额外常驻操作栏 |

单元测试验证状态与版本，浏览器测试验证图片实际可见和网络次数；原生验收必须使用完整隔离 Tauri 应用与真实鼠标点击。先用合成资料完成生产构建回归，再做正式安装交付；不以这次 WKWebView 组件探针代表完整应用已修复。
