# 书库显示诊断 · 2026-10-28

以下为修复前的排查记录，行号和失败计数均对应当时源码。用户随后授权移除自动大小并修复，下述堵点已完成源码修复，当前验证与边界见 `PROGRESS.md` 顶部的「2026-10-28 书库显示修复与收尾（源码）」。收尾还修正了无效 URL 意外关闭自动排序规则，以及虚拟网格在换列边界上的宽度计量与同步循环异常。原诊断阶段只排查与记录，不修改产品实现。诊断当时运行的是 `.glossa-dev/target/debug/Glossa` 与 Next Dev；当时日常安装包仍为 10 月 23 日版本，不能用安装包旧解释开发版的现象。工作区已有多项未提交修改，本轮保留。

## 1. 封面大小没有直接控制封面大小

- `Bookshelf.tsx:156` 将 `libraryCoverWidth` 用作 `repeat(auto-fill, minmax(min(width, 100%), 1fr))` 的最小轨道宽度。列数不变时，`1fr` 继续均分可用空间，封面实际大小不变；跨过阈值后突然少一列并放大。这是滑杆语义与布局算法不一致，不是事件完全没有触发。
- 在 1100px 隔离视口中，把滑杆从 188 依次调到 192、196、200、204、208、212、216、220，实测轨道宽度为 **204、204、204、204、204、258、258、258、258px**。这是轨道宽度，书卡还含内边距，不应误称精确封面宽度。
- `ViewMenu.tsx:124` 先等待宽度写盘，再关闭自动列数；自动模式下 `ViewMenu.tsx:52` 又忽略存储宽度并读取当前轨道。延迟首次保存后，拖到 260 的滑杆仍显示 168，直到保存完成才进入手动模式。连续输入直接调用全配置保存，没有拖动草稿与提交边界。
- 修复方向：让当前拖动值即时控制展示，换列单独推导；宽度和自动模式作为同一次偏好变更，持久化不阻塞预览，继续兼容旧固定列数。

## 2. 菜单与书库使用不同的有效状态

- `ViewMenu.tsx:41,61,62,70,79` 从保存的设置读取封面模式、主次排序及方向；`Bookshelf.tsx:255` 则优先使用 URL 的 `cover/sort/order/thenSort/thenOrder`。布局模式已经兼顾 URL，其余字段没有统一。
- 隔离复现：设置为填满、URL 为 `cover=fit`，实际封面已经完整显示，菜单却仍选中填满。
- 隔离复现：设置为降序，URL 为 `sort=author&order=asc`，书库实际升序，按钮却显示降序；第一次点方向按钮只把保存值改为升序，实际书目首项保持 `Original 7`，URL 也仍为升序。真实菜单点击已复现，非仅静态推断。
- `Bookshelf.tsx:337` 的旧参数清理还硬编码删除 updated/desc/crop/grid，而消费处回退的是当前个人偏好；带旧页面参数的恢复／历史导航因此也存在改变有效值的路径。本轮未独立测试所有历史导航组合。
- 修复方向：显示、排序和菜单共用同一有效偏好解析；清理 URL 只能删除与真实回退值等价的参数，并覆盖历史返回及旧快捷入口。

## 3. 次级排序“无”不能表达明确关闭

- `ViewMenu.tsx:74` 与 `libraryUtils.ts:94` 都把作者浏览中的 `none` 解释为自动按系列排序。
- 菜单同时提供“无”选项；选择后只保存 `none` 并删除 `thenSort`，没有区分未设置与用户明确关闭。真实 select 操作后仍回到 `series`。
- 这是状态语义冲突，不是作者名或系列数据有误。应区分自动默认与明确无次级排序，并迁移兼容旧偏好；主排序已经有 `librarySortByAuto`，次排序尚无对应的明确意图。

## 4. 保存失败后，界面状态与磁盘状态分离

- `helpers/settings.ts:255` 先原位修改内存并通知 UI，随后等待保存；异常没有恢复或待重试状态。菜单处理器没有提供错误反馈。
- 故障注入复现：首次保存 220 失败，第二次选择 220 被 `settings[key] !== value` 判断跳过；底层保存只被调用一次。
- 布局、封面和排序的 URL 更新位于 `await saveSysSettings` 之后，失败还可能留下“控件已改、URL 未改”的分裂状态。
- 此项证明失败恢复路径有缺陷，**不证明当前用户磁盘正在报错**。只读检查确认开发版已有显示偏好写入磁盘。
- 修复方向：设置提交应有可辨认的失败状态和同值重试，不能将内存相等当作持久保存成功；避免用旧整对象覆盖后续编辑。

## 5. 旧阅读窗口会回写整份旧显示偏好

- `utils/settingsSync.ts:55` 的跨窗口载荷包含阅读全局对象、显式插件／分组／云开关等，却没有书库显示字段；`mergeSyncedGlobalSettings` 保留接收窗口自己的旧 `libraryCoverWidth/libraryShowAuthor/...`。
- `store/settingsStore.ts:64` 与 `services/settingsService.ts:186` 保存整份设置；`ReaderContent.tsx:118,188,199` 在更新打开书目、返回书库或关闭阅读器时仍会提交该窗口的整对象。旧阅读窗口即使收到广播，也会把书库后来改好的显示偏好写回旧值。
- 使用真实广播、合并和保存服务，以及合成双窗口快照／内存文件系统复现：先保存书库宽度 **260、隐藏作者**，旧阅读窗口接收实际广播并再次保存后，磁盘变成 **156、显示作者**。该探针没有启动两个真实 WebView，但验证了它们实际共用的协议与持久保存链路。
- 当前原生开发应用有一个书库窗口和三个阅读窗口，此路径与现场有关；本轮未关闭个人阅读窗口来触发覆盖，不宣称已在个人配置上实操复现。
- 修复方向：按字段与明确修改意图保存，写入时合并最新持久状态；跨窗口同步书库偏好，不能只扩大广播后继续依赖整对象覆盖。关闭窗口还会重新加载设置，因此旧值可能随后立刻回到书库。

原生只读复核补充：

- 无障碍树显示书库路由为 `/library?groupBy=none`，没有搜索与具体分组；最近阅读开关开启。仅截取该开发版书库窗口，当前画面仍是四本未读、没有最近阅读条目。
- 同时只读统计磁盘：四本可见书中，一本已有 `progress`，且未标成未读、读完或放弃，符合 `isCurrentlyReadingBook`。原生画面与磁盘已有状态不一致证据，不能直接归因于没有在读数据。
- `library/page.tsx:492` 明确只在收到 `close-reader-window` 时重读书库和设置。`useLibrary.ts:16` 已加载后跳过重读；阅读器更新自身 store 与磁盘，没有普通进度的跨窗口通知。现有 BroadcastChannel 处理的是删除，并未补齐阅读进度刷新。
- 因此“阅读窗口仍开着时，最近阅读及书卡进度滞后”有明确源码路径，也与当前三个阅读窗口同时打开的现场吻合；本轮没有关闭个人阅读窗口、读取其 JS 内存或执行完整原生进度交互，具体现场归因仍保留这一验证边界。未修改个人书籍与偏好。
