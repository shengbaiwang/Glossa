# 开书变慢：诊断与简明方案（2026-10-30）

用户反馈各种书都慢。先完成诊断与方案；随后用户授权执行，源码修复与验证见第 4 节。未改个人书库、配置或日常安装版，也未重启正在使用的 Glossa Dev。

结论：优先缩短新阅读窗口的公共启动路径，再修复 EPUB 导航缓存复用；现有证据不足以支持重写阅读引擎。已确定两个代码缺陷，并量出开发脚本的明显加载负担；尚未取得用户实际书籍从双击到正文可读的完整原生分段追踪，不能声称每项已解释实际等待的固定比例。

## 1. 已确认的事实

### 开发阅读窗口加载依赖过重，影响所有格式

- 当前运行 `Glossa Dev`，Next.js 16.2.11；此前为恢复开发服务，将原生开发命令切换到 `next dev --webpack`。这项变更有既有故障背景，见 `web-import-dev-recovery-2026-10-30.md`，本轮未回退。
- 当前 `app/reader/page.js` 未压缩 **55,237,097 字节**、1,039 个模块；`app/layout.js` **16,210,826 字节**。这是开发产物，包含 eval/source map，不能当成生产包体。
- 阅读页脚本中 `react-icons/ri`、`bs`、`lu`、`fa` 四个整包合计约 **22.6 MB**。`ReaderContent.tsx` 静态引入设置、备份、迁移、缓存管理等非首屏窗口，其依赖进入阅读启动图。Next 默认已列入 react-icons 的包导入优化，重复添加同一配置不能作为已验证解决方案。
- 对正在运行的服务连续发出 3 次无条件 gzip 请求：阅读页脚本实际传输 **11,885,288 字节**，耗时 **1.386 / 1.565 / 1.633 秒**；layout 约 **4.00 MB / 0.463 秒**。这些是本机 HTTP 请求，包含服务器压缩与传输，未计脚本执行、原生文件 I/O 或正文显示；两个资源可并行，不能简单相加为开书耗时。
- 响应为 `Cache-Control: no-cache, must-revalidate`，支持 ETag；带当前 ETag 的请求返回 **304 / 0 字节 / 1.94 毫秒**。阅读页与 layout 的 URL 在连续请求间相同，main-app 和 webpack runtime 带变化时间戳。因此不能断言每次开新窗口都会重新下载 11.9 MB，也没有把条件缓存错误地等同禁用缓存。
- `Reader.tsx` 在 `libraryLoaded` 后才挂载阅读内容；新窗口的 `useLibrary.ts:24` 先读设置、再读整个书库。原生封面 URL 准备主要是拼接路径，本轮没有证据证明全库封面图片读取是主要延迟。

这是与“各种书都慢”最匹配、应优先优化的公共路径。没有进行切换打包器前后的原生 A/B，不将相关性当成唯一根因证明。

### EPUB 在开发模式下忽略有效导航缓存

`src/store/readerStore.ts:250` 仅允许 production 复用有效导航缓存；development 每次执行 `computeBookNav`，并等待缓存保存后才继续显示阅读器。

隔离调用真实 `initViewState` 的三组对照通过：

| 模式与缓存 | 导航重算次数 | 保存次数 |
| --- | ---: | ---: |
| development，当前版本 4 | 1 | 1 |
| production，当前版本 4 | 0 | 0 |
| production，旧版本 3 | 1 | 1 |

对含片段锚点的目录会逐章读取文本、解析 DOM；超过 64 节且目录稀疏的书，还会扫描全书寻找嵌入目录。不是所有 EPUB 都会遍历全部正文，也不是 PDF 的加载原因。

### 服务初始化存在并发与失败恢复缺陷

`src/services/environment.ts:44–60` 在动态导入完成后才创建实例，且在 `init()` 完成前就发布实例；失败时也未清除。

直接编译并执行该源码、仅替换底层服务 I/O 的隔离实验，对 tauri/web 两条分支均复现：8 个同时到达的调用触发 **8 次构造、8 次初始化**；初始化未完成时，迟到调用已返回；失败后的下一次调用返回旧的损坏实例。顺序调用对照只初始化 1 次。共 16 个诊断断言通过，表示缺陷得到复现，不表示修复完成。

当前 `Providers` 会等待服务后才渲染阅读子组件，具有一定门控；本轮没有观测到真实开书一定发生 8 次初始化。这是已证实的可靠性与潜在重复 I/O 问题，不能据此编造用户实际耗时。

## 2. 真实引擎对照

使用原创、内存生成的 12 章、128 章以及 128 章稀疏目录 EPUB，每种引擎每组运行 5 次。真实 `DocumentLoader`、导航算法和 Foliate 显示末章，缓存恢复验证目录相同且不读取/解析章节。采用 Chromium 和系统 WKWebView，后者为独立无持久存储窗口。

| 引擎 / 夹具 | 导航重算中位数 | 缓存恢复中位数 | 导航阶段文本/DOM 调用 |
| --- | ---: | ---: | ---: |
| Chromium / 12 章 | 8.94 ms | 0.10 ms | 12 / 12 |
| Chromium / 128 章 | 97.90 ms | 0.56 ms | 128 / 128 |
| Chromium / 128 章稀疏目录 | 163.78 ms | 0.56 ms | 256 / 129 |
| WKWebView / 12 章 | 10 ms | 0–1 ms | 12 / 12 |
| WKWebView / 128 章 | 89 ms | 约 1 ms | 128 / 128 |
| WKWebView / 128 章稀疏目录 | 148 ms | 约 1 ms | 256 / 129 |

WKWebView 计时精度约 1 ms，0 不能解读为无成本；稀疏目录重算样本范围为 140–328 ms。缓存恢复计时包含 JSON 复制和 hydrate，不含持久缓存读取与文件身份核验。调用数不是物理磁盘读取数。

这些夹具文本约 10 KB/章，可压缩性高，没有图片、字体和原生 Rust/IPC 文件读取；结果证明可避免重复目录工作，不代表真实大书、全部格式或整应用端到端的提速比例。

本轮有效验证：

- 现有单元回归：6 文件 / 101 项通过，涵盖环境、阅读状态、导航、文档、内容来源和书库仓库。
- 缓存模式对照：1 文件 / 3 项通过。
- 真实 Chromium 基础阅读：3 文件 / 6 项通过，涵盖真实 PDF、损坏 PDF 拒绝、网页转 EPUB 离线图文/公式/表格/脚注、位置恢复。
- 新增 Chromium 引擎诊断：1 文件 / 3 项通过，15 次真实开书。
- 系统 WKWebView：3 组 / 15 次真实开书通过。
- 初始化源码隔离实验：tauri/web 两分支共 16 个断言通过。

早期 Vitest 动态服务 mock 未隔离的报错不作为产品证据，已改用源码隔离实验；临时失败测试已移出正常测试集并恢复本轮对原测试的修改。Playwright WebKit 未安装；改用系统 WKWebView。原生探针最初的 404、路径别名和环境变量问题均属于测试配置，修正后完整重跑。未执行完整应用所有测试或发布版性能对照，本轮也没有产品实现改动。

## 3. 原建议实施顺序（现已授权）

1. **缩小阅读启动路径。** 设置、备份、迁移、关于等窗口按需加载，清理整套图标包进入首屏的依赖；新窗口优先从权威书库数据库取得当前书记录和必要设置，全库加载延后。保持用户现有多窗口习惯、应用锁和数据一致性。先建立点击、脚本就绪、服务就绪、文件打开、定位恢复、正文可读的分段计时，再比较优化前后。
2. **修复重复工作。** 开发/生产都可复用经验证的导航缓存，键绑定文件身份、修订和算法版本；来源变化继续完整核验。服务初始化共用一个进行中的 Promise，成功后才发布，失败后允许重新初始化。首屏不等待派生缓存的落盘，失败可重建且不阻断正文。
3. **再做局部算法重构。** 将“必须完成全书工作才能显示”改为“先解析并恢复当前阅读位置，再有界补齐目录增强和邻章预取”。保留原有目录/CFI/笔记语义，不重建阅读器、不跳动当前页；DOM 工作分片让出主线程，纯解压/文本计算在适合时使用现有 Worker。任务可取消并拒绝旧书迟到结果。PDF 先显示原页，再按既有规则核验并加载派生目录/OCR，不降低完整身份核验或目标标题核验标准。

不先重写 EPUB/PDF 阅读引擎，也不盲目增大并发、开启整书索引或恢复后台 AI 任务。第三步只重构实测占比高的部分。

后续验收以相同书库规模、相同原书、冷/热打开分别测量，覆盖开发/发布、原生新窗口/同窗口、EPUB/文本 PDF/扫描 PDF/网页书，记录从点击到可读及可翻页的 p50/p95、长任务和内存。不得用转圈消失代替正文可读，不先承诺未测得的固定提速百分比。

## 4. 授权后的实施

### 公共启动路径

- 阅读器中的设置、书籍信息和传输面板使用条件式动态导入；关于、备份、缓存管理和迁移保留轻量事件入口，首次打开才加载实际内容。首次打开、加载期间关闭、再次打开和 React StrictMode 重复 effect 均有回归覆盖。
- `useLibrary(bookIds)` 优先从原生/Node 权威数据库按主键读取当前书记录，仅准备当前书的封面地址；完整书库在正文恢复位置后经 rAF 与定时器再加载。普通进度/书库更新保留完整性状态，只有完整读取显式标记 `libraryLoaded`；完整读沿既有修改时钟保留等待期间的新进度、分组和改名。切换路由、关闭窗口会拒绝旧查询迟到发布；完整读以磁盘成员关系为准，不带回过期普通行。合并函数移入轻量模块，保留原导出，避免共享 store 因此引入文档解析和 OPDS 依赖。
- 同 hash 写入及同步元数据/旧版删除记录在完整加载后合并最新个人字段；不让等待中的旧输入覆盖新进度。乐观编辑保存失败时，仅在当前字段仍属于该次编辑的条件下局部恢复，保留后续阅读进度和其他编辑。部分书库不会提前放行完整书库同步。
- 原生/Web 服务初始化各复用一个进行中的 Promise，仅成功后发布实例；失败释放进行中状态，允许后续重试。

### EPUB 导航局部重构

- 开发与生产都复用当前算法版本且来源有效的缓存。绑定书籍完整导入指纹、移除代际、实际来源路径、大小与修改时间。托管书正常打开不重复整书哈希；外部文件首次绑定或检测变化时完整核验，不可靠或缺完整身份的来源不复用/保存缓存。缓存结构损坏安全回退，派生缓存不影响正文读取。
- 缓存缺失时，先用结构信息计算基础位置，显示原有目录、恢复保存的 CFI；首次正文定位完成并获得一次绘制机会后才后台增强目录。后台最多 4 个章节同时处理，在章节之间让出事件循环；仍完整处理原算法目标，没有抽样缩减目录覆盖。
- 同窗口同书初始化顺序衔接，后来的视图复用已发布文档；导航任务按文档共享一次，副视图不会重置已增强目录。关闭主视图后其他存活视图继续持有任务，最后一个关闭才取消；失败的初始化也释放所有权。计算使用私有 TOC/section 副本，完成后重新核对来源和当前文档，再同步发布完整派生字段；更新现有 Foliate TOCProgress，不改变 viewerKey、不重载正文。缓存保存继续核对最初 token；取消初始化时销毁尚未移交共享状态的文档并关闭新文件。
- 增加本机有界 User Timing：`glossa.reader.service-ready`、`file-open`、`document-parse`、`config-read`、`navigation-cache-read`、`store-ready`、`position-restored`、`window-to-position`、`navigation-enhanced`。可在 WebView DevTools 的 Performance/User Timing 查看；每名称最多保留 32 条，不含书名/路径，也没有新增遥测。`window-to-position` 从本窗口 navigation 起算，不能替代跨窗口双击时间。
